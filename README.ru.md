## 💡 О проекте

Сервис получает из базы данных населённый пункт (город или регион) и его полигон, строит внутри границ сетку географических точек, отправляет координаты каждой точки в **Yandex Geocoder API**, а затем обрабатывает сведения о районах и сохраняет результат в CSV.

Задача возникла из практической потребности: Yandex Geocoder не предоставляет все районы города одним запросом. Вместо этого необходимо геокодировать множество точек на территории населённого пункта и собрать полученные данные. Проект автоматизирует этот процесс и разбивает его на восстанавливаемые этапы ETL.

**Что демонстрирует проект с инженерной точки зрения:**

- Полный ETL-цикл: геометрия → внешний API → преобразование → сохранение.
- Оркестрация в Airflow: передача событий между DAG через **Assets**, а не только запуск по расписанию.
- Разделение бизнес-логики, внешних сервисов и хранения данных посредством интерфейсов.
- Модульные и интеграционные тесты, а также проверки DAG.
- CI на GitHub Actions.

## ⚙️ Как это работает

Пайплайн состоит из четырёх связанных DAG Airflow. Завершение одного этапа публикует событие Asset, которое запускает следующий этап.

```text
geocoding_polygon → geocoding_points → geocoding_requests → geocoding_save
      │                    │                   │                  │
      ▼                    ▼                   ▼                  ▼
  Полигон из БД     Сетка координат     Запросы к API       Итоговый CSV
                     внутри полигона     для каждой точки    в MinIO / S3
```

1. **geocoding_polygon** — получает полигон населённого пункта из PostgreSQL и сохраняет его в MinIO в формате GeoJSON.
2. **geocoding_points** — строит сетку точек внутри полигона с заданным шагом в метрах (с использованием `pyproj` и геометрических операций).
3. **geocoding_requests** — выполняет запросы к Yandex Geocoder API для точек. Использует динамическое создание задач (`task.expand`), повторные попытки и отдельный Airflow Pool для управления параллелизмом. Обработка может продолжаться последовательными партиями с учётом доступных API-ключей.
4. **geocoding_save** — собирает ответы геокодера, преобразует результаты, выполняет дедупликацию данных о районах и сохраняет итоговый CSV в MinIO.

## 🏗️ Архитектура

Проект использует разделение на слои и абстракции для внешних зависимостей: прикладная логика не привязана напрямую к конкретной реализации геокодера, SQL-репозитория или формата сохранения результатов.

```text
backend/
├── api/          # Клиент Yandex Geocoder, модели и сервис
├── database/     # Подключение к PostgreSQL, репозиторий и сервис
├── geometry/     # Геометрические операции и сетка точек (Shapely, pyproj)
├── transformer/  # Преобразование и дедупликация данных
├── etl/          # Координация этапов ETL
└── writer/       # Сохранение результата в CSV
```

Интерфейсы `GeocoderClient` и `PlaceRepository` позволяют заменять соответствующие реализации, не переписывая остальную бизнес-логику.

Промежуточные данные — полигон, координаты и ответы геокодера — хранятся в MinIO в рамках отдельного задания. Это позволяет передавать большие наборы данных между DAG без хранения всего содержимого в XCom, а также повторно запускать отдельные этапы после сбоев.

![Структура хранения данных в S3](docs/images/s3-storage.png)

## 🚀 Начало работы

### Требования

- Docker Engine или Docker Desktop с Docker Compose.
- Действующий API-ключ Yandex Geocoder и доступ к API.
- PostgreSQL с данными о населённых пунктах и их полигонами. Контейнер `postgres` из Compose используется для метаданных Airflow; данные о населённых пунктах настраиваются отдельно через переменные `DB_*`.

### Конфигурация

Из корня репозитория создайте файл настроек:

```bash
cp .env.example .env
```

Укажите реальные значения для `YANDEX_GEOCODER_API_KEY` и `DB_*` в `.env`. Не публикуйте `.env` и файлы с API-ключами. При подключении к базе данных из контейнера используйте адрес хоста, доступный из Docker-сети: `localhost` внутри контейнера не указывает на компьютер, на котором запущен Docker.

SQL-запрос для чтения населённых пунктов вынесен в отдельный файл: `sql/example/t_place.sql`. Он рассчитан на пример таблицы `t_place`; под собственную схему БД измените SQL-файл и при необходимости путь `DB_SQL_FILES_PATH`.

Для работы DAG с MinIO в Airflow требуется настроить подключение с идентификатором **`minio_s3`**, используемым в коде `S3Hook`. Укажите S3-совместимый endpoint контейнера MinIO (`http://minio:9000`) и учётные данные из конфигурации Compose. Сам контейнер `minio-init` создаёт бакет `geocoding`, но не заменяет настройку Airflow Connection.

### Запуск через Docker Compose

```bash
docker compose build
docker compose up -d
```

Для просмотра журналов:

```bash
docker compose logs -f
```

После запуска доступны:

- **Airflow:** http://localhost:8080
- **MinIO Console:** http://localhost:9001

Контейнер `airflow-init` выполняет миграции БД метаданных Airflow и создаёт пул `yandex_geocoder` с **5 слотами**, если он ещё не существует. При необходимости измените число слотов через интерфейс Airflow в соответствии с разрешённым параллелизмом и ограничениями вашего API-ключа.

### Запуск обработки

Откройте интерфейс Airflow и запустите DAG `geocoding_polygon` вручную. Параметры запуска:

| Параметр | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `place_id` | Идентификатор населённого пункта в вашей БД | `37592` (пример из проекта) |
| `distance_meters` | Шаг сетки координат в метрах | `1000` |
| `requests_limit` | Максимальный размер партии запросов | `1000` |

Замените пример `place_id` на идентификатор, существующий в вашей базе. Дальнейшие DAG запускаются по событиям Assets.

### Несколько API-ключей и ограничения запросов

Для использования нескольких ключей поместите по одному ключу в строке файла `data/api_keys.txt`. Если файл отсутствует, используется `YANDEX_GEOCODER_API_KEY` из окружения. Файл с ключами не следует добавлять в Git.

Пул ключей атомарно учитывает попытки HTTP-запросов и переключается на следующий доступный ключ при исчерпании установленного дневного лимита. Лимит по умолчанию — **1000 попыток на ключ в сутки**; его можно настроить переменной `YANDEX_GEOCODER_API_KEY_LIMIT` (при соблюдении лимитов поставщика API).

Ключи с HTTP 403 помечаются как отключённые, а с HTTP 429 — как исчерпанные до следующего дня по UTC. Счётчики и хеши ключей хранятся в `data/api_keys.state.json`, без самих секретов. При наличии необработанных точек DAG запросов формирует следующую партию, если доступен API-ключ с оставшимся лимитом.

### Секреты и дополнительные настройки

Переменная `ENV_PATH` позволяет указать дополнительный файл окружения с локальными настройками. Храните такие файлы и реальные учётные данные вне репозитория.

## ✅ Тестирование и контроль качества

Проект включает модульные тесты бизнес-логики с подменёнными зависимостями, интеграционные тесты с PostgreSQL в Docker (`testcontainers`) и имитацией Yandex API (`pytest-httpserver`), а также проверки структуры DAG в окружении Airflow.

Для локальных проверок потребуются Python 3.14, зависимости проекта и запущенный Docker (для интеграционных тестов).

```bash
python3.14 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

ruff format --check .
ruff check .
mypy backend airflow/dags

pytest tests/unit tests/integration
docker compose --profile tests run --rm --no-deps airflow-tests
```

Последняя команда запускает тесты DAG в контейнере Airflow; профиль `tests` предназначен именно для тестирования.

В GitHub Actions настроены проверки Ruff, Mypy, модульных и интеграционных тестов, а также тестов DAG при push и Pull Request в `develop` или `main`.
